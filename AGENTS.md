## Unity Safety Rules

- No direct C# caller does **not** mean unused. Unity invokes lifecycle methods such as `Awake`, `Start`, `OnEnable`, `Update`, `FixedUpdate`, `LateUpdate`, `OnDisable`, `OnDestroy`, `OnValidate`, and trigger/collision callbacks. This repository contains lifecycle callbacks throughout `Assets/Scripts/`.
- `[SerializeField]` fields can be populated from scenes, prefabs, and `.asset` files. Inspect serialized consumers before deleting, renaming, changing type, or changing defaults.
- Inspector references are not ordinary C# references. Confirm GameObject/component wiring in scenes and prefabs whenever behavior depends on it.
- UnityEvents can create persistent calls that semantic C# tools cannot see. Inspect serialized event bindings before treating a method as dead.
- ScriptableObjects are referenced by assets as well as code. Check `Assets/ScriptableObjects/` and its consumers before changing a data contract.
- Animation events and Animator state behavior can invoke code indirectly. Inspect clips/controllers and component wiring when modifying animation-facing methods; repository animation assets live under `Assets/Animations/`.
- Runtime loading hides static dependencies. This repository has `Assets/Resources/` and calls to `Resources.Load`, including recognition/template and UI font paths. Preserve load paths unless all consumers are updated.
- Reflection and runtime type lookup can hide dependencies. Search literal member/type names as well as semantic references when relevant.
- New Input System wiring includes serialized action assets and `ProjectSettings/EditorBuildSettings.asset` configuration, not only C# references.

## Unity Asset Safety

- Preserve every `.meta` file and its GUID relationship. Never regenerate, delete, or replace a `.meta` file casually.
- Do not casually move or rename assets. Prefer Unity-aware moves so the asset and `.meta` stay together, then inspect all affected references.
- The repository uses Force Text serialization (`ProjectSettings/EditorSettings.asset`) and UnityYAMLMerge attributes for `.unity`, `.prefab`, and `.asset` files (`.gitattributes`). Review those diffs as serialized object changes, not ordinary text edits.
- Avoid direct scene/prefab YAML editing unless the task requires it and the exact object/reference impact is understood. Validate the result in Unity afterward.
- Avoid unnecessary asset reserialization, import churn, or broad Inspector changes.
- Before renaming a serialized field, inspect existing assets and evaluate `UnityEngine.Serialization.FormerlySerializedAs`. Existing compatibility examples include `Assets/Scripts/Data/BossPhase.cs` and `Assets/Scripts/Data/LevelConfigSO.cs`.
- Do not change GUIDs, file IDs, execution order, tags/layers, input bindings, or build-scene membership as incidental cleanup.

## Commit and Pull Request Delivery

Use this delivery order: **verify → review → commit → push → pull request**. Verification and diff review happen before staging. Stage only files owned by the current task; never sweep unrelated dirty-worktree changes into a commit.

The exact user phrase **`ship this`** authorizes Codex to complete that delivery sequence without another confirmation:

1. Run and report the relevant checks, then review the complete diff.
2. If currently on `dev` or `main`, create a compliant task branch before committing. Otherwise validate the current branch.
3. Stage only task-owned files, create one or more compliant commits, and push the current task branch.
4. Open a pull request targeting `dev` unless the user explicitly names a different base.
5. Create a ready pull request only when every required check is `PASS` or `NOT APPLICABLE`. If a relevant check is `FAIL`, `NOT RUN`, or `BLOCKED`, create a draft and document each unresolved check.

`ship this` never authorizes merging, force-pushing, staging unrelated files, bypassing validation, or rewriting published history.
